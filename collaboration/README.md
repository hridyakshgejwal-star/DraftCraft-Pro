# DraftCraft collaboration protocol 1

Run `DRAFTCRAFT_CREATE_KEY='<at least 20 random characters>' node collaboration/server.mjs` from the source root after `npm ci`. The default binds to 127.0.0.1:8787; data is written atomically, mode 0600, in `collaboration-data/`. Back up this directory. Session credentials are stored as hashes. Screenplay content is not end-to-end encrypted at rest.

For deployment, build `docker build -f collaboration/Dockerfile -t draftcraft-collaboration .`, mount a writable `/data` owned by uid 1000, set DRAFTCRAFT_CREATE_KEY, and place behind a TLS reverse proxy forwarding WebSocket upgrades. Set DRAFTCRAFT_ORIGINS to a comma-separated list of allowed web origins. The desktop origin draftcraft://app is allowed. Keep the create key private and use HTTPS/WSS outside localhost. Public hosting, domain certificates, monitoring and backups are the operator's responsibility; none is provisioned by the application.

Creating a room requires bearer authentication. The host receives a host credential and invitation code. Invitation holders remain pending and receive no screenplay content until the host grants edit or view permission. Approved clients receive a resumable credential. Local edits use Y.Text and stable record identities; reconnect sends a state vector and the client's missing updates. Messages and presence represent actual connected clients and are transient. The server checks role permissions and bounds message/document sizes.

The first version synchronizes screenplay paragraphs, Beat Board records, outline markers/lanes, flow lines, template and document metadata. Native save locations, private Table Read settings, production review/tag/locking state and credentials stay local. Scalar simultaneous metadata changes use Yjs map conflict resolution. No overlapping Table Read audio or production workflow collaboration is claimed. End a session before production locking or global format conversion. Local native saving continues independently.
